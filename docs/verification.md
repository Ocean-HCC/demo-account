## 4. 唯一「注意」项 T7 的判定：设计边界，非缺陷

T7 报告五只标的日线都「只到 2026-09-24」，而期望值是 2026-09-28。经查证这是**有意设计的保守行为**：

- `backend/src/demo_account/market/tsp_source.py:4` 明确写明：TSP 注入到日线里的盘中实时蜡烛
  （`is_live`）**一律丢弃**，结算只用收盘后落盘的日线；实现见同文件 `:92`（`if row.get("is_live"): continue`）。
- TSP 在实时行情开启后，会把当日实时 enriched 行以 `is_live: true` 注入日线响应
  （`app/api/kline.py:_latest_live_candle`）。`verify_tsp.py:520` 过滤掉 `is_live` 行后，
  最后一条**非 live** 日线自然落在上一个交易日。
- 底层数据并不陈旧：TSP `enriched` 已到 2026-09-28，且 `/api/kline/daily/latest` 对 600000.SH
  返回了当日行（`date: 2026-09-28, close: 9.16, is_live: true`）。
- 该过滤不影响撮合与结算的取价：即时单走 snapshot 路径，结算走落盘日线；F1 已用真实数据跑通验证。

因此 T7 是「实时行情开启 + 适配器只认落盘日线」的必然结果，demo-account 的行为是正确且安全的。
它在 M5 判定中属「注意」而非「失败」，不构成可行性阻断。

## 6. 风险与遗留事项

### 6.1 TSP 必须以「清洗过的代理变量」启动（重要）

当前 shell 环境的 `NO_PROXY` / `no_proxy` 含 `[::1]`：

```
NO_PROXY=localhost,127.0.0.1,::1,[::1]
```

httpx 在构造客户端时会把 `NO_PROXY` 每一项当 URL 解析，`[::1]` 会让它抛
`httpx.InvalidURL: Invalid port: ':1]'`，导致**该进程内所有基于 httpx 的数据源全部失效**
（TSP 自带的 `data-pull-issues-for-fix-agent.md` 已把此记为 P0-1）。验证过程中已实测复现。

当前运行的 TSP 进程（PID 36224）**没有**这两个变量，所以数据链路正常。**但重启 TSP 时必须清洗**，
否则轮询与日K同步会静默失败：

```powershell
cd D:\project\tick-stock-panel\backend
python -c "import os,uvicorn; os.environ['NO_PROXY']='localhost,127.0.0.1'; os.environ['no_proxy']='localhost,127.0.0.1'; uvicorn.run('app.main:app', host='127.0.0.1', port=3018)"
```

demo-account 自身不受影响：它默认不读系统代理（`DEMO_ACCOUNT_HTTP_TRUST_ENV=false`），公开接口
（深交所日历、东财停复牌与分红、新浪指数）与 TSP 本机访问均正常。

TSP 运行在 **TickFlow Free 档**，免费档日K 有一定滞后（实测免费接口最新到 2026-09-24，更近的交易日

## 9. 复核更正（2026-09-29）

复核这份报告和入库的样本后，下面两处判断需要更正。

### 9.1 T7「注意」其实是阻断性缺陷

第 4 章认为这是设计边界，这个判断不成立。

- **现象**：T7 在 18:06 运行时，TSP 已经收盘定版（`market_phase: close_final`、`final_sync_done: true`）。可是样本里 09-28 这一行仍带 `is_live: true`，而且带有 `raw_close` 等落盘字段，说明它是已落盘的行被实时值覆盖后返回的。
- **原因**：北京时间当天 24:00 之前，TSP 都会用实时值覆盖当日行并打上 `is_live`，而原来的适配器会丢弃所有 `is_live` 行。
- **后果**：24:00 之前取不到当天的日线。只要账户有持仓或挂单，16:00 的结算就会因为缺收盘价而失败，重试到 23:00 后放弃，于是收盘单不成交、T+1 不解锁、净值不定版。
- **F1 为什么通过了**：F1 结算的是上一个交易日（09-24），那天的行不会被覆盖。

处理办法：
- 实现文档 3.2 改为：TSP 收盘定版后，把当日的 `is_live` 行当作当日日线。
- verify-tsp 做两处调整：一是取不到最近一个已收盘交易日的日线时，T7 判为「失败」；二是 F1 改为结算最近一个已收盘的交易日，所以交易日 16:00 以后运行时结算的就是当天。
- 同时补一条规则：结算拖到第二天还没完成时，暂停交易并按日期顺序补结算（方案 4.4）。

### 9.2 ETF 实时拉取不能关

3.2 节认为 `realtime_pull_etf` 保持关闭也能取到 ETF 行情，依据是 18:06 取到了 510300.SH 的当日价 4.417。这个依据站不住：TSP 的 ETF 当日行情读自 ETF 缓存，18:06 时这份缓存是刚跑完的盘后管道写入的。到了盘中，缓存日期还停在前一个交易日，ETF 预计没有实时快照，即时单、限价单和开盘单都无法成交。实现文档 3.2 已把开启 ETF 实时与日线拉取列为交易 ETF 的运行前提。

**补充更正（2026-09-29 午间核实）**：上面的诊断方向对了，但「打开 `realtime_pull_etf` 即可取到 ETF 盘中行情」这一步**在本机不成立**——开关只决定 TSP 去不去订阅 ETF，而上游 fuyao 快照根本不返回 ETF 行。撤下开关后做了全量核对（非抽样）：

| 核对项 | 结果 |
| --- | --- |
| fuyao 快照 `/api/a-share/prices/snapshot` | 5578 行 / 5578 个去重标的 |
| 其中 ETF 形态代码（51/15/56/58/16/50 开头） | **0** |
| TSP 维表 `data/instruments_etf/instruments_etf.parquet` | **1732** 只 ETF |
| 两边交集（能取到实时快照的 ETF） | **0** |
| `510300.SH` | 维表里在 ✅，快照里不在 ❌ |
| `etf_symbol_count`（开关为 true 时实测） | 仍为 **0** |

fuyao 插件声明的数据集是 `realtime / daily / adj_factor / financial`，实时端点只有 `/api/a-share/prices/snapshot`（A 股全市场）与 `/api/a-share-index/prices/snapshot`（指数），**没有 ETF 实时通道**。要补上只有两条路：升级 TickFlow 到 Starter+（ETF 实时走 `quotes.get_by_universes(["CN_ETF"])`），或接入带 ETF 实时能力的自定义源（`stock-sdk` 插件声明支持 realtime，但本机 `node_modules` 未安装、状态不可用）。

**处置（发起者决定）**：本机不做 ETF，不再追这条路径。因此 `verify-tsp` 的 T5 会持续显示「ETF 没有实时快照」这一「注意」项——它是环境能力边界，不是代码缺陷，**不影响「报告无失败项」的判定**。ETF 的日线、复权与成交路径本身是通的：F1 中 510300.SH 已按真实收盘价 4.417 成交，ETF 日K 353816 行、覆盖 1675 只（见 3.2 节）。

### 9.3 M5 状态

**关键证据二：唯一缺当日行的是 ETF。** TSP 侧 `daily` / `enriched` / `adj_factor` 均已到
